# מדריך כניסה לצד השרת (Supabase Auth)

המדריך מיועד למי שכותב את צד השרת (Next.js על Vercel, מתוך Claude Code).

## עקרונות

- **כל הגישה למסד היא מצד השרת**, עם מפתח `service_role`. המפתח הזה לא נשלח לדפדפן ולא נשמר ב-GitHub, רק במשתני הסביבה של Vercel.
- **אין הרשמה עצמית.** "Allow new users to sign up" כבוי. משתמש נפתח רק על ידי השרת.
- **מספר טלפון מלא לא יוצא מהשרת.** הדפדפן רואה רק טלפון מוסתר (050-***0201) של המשתמשים ששייכים לספק או לגן שהוקלד.
- **ספקים וגננות:** קוד SMS. **צוות אריאל:** חשבון העבודה של אריאל (Microsoft).
- **חיבור השרת למסד:** הסכמות של המערכת (`core`, `ops`, `access` וכו') לא חשופות כרגע ב-Data API של Supabase. יש שתי דרכים: חיבור Postgres ישיר מהשרת (Connection pooler), או הוספת הסכמות ל-"Exposed schemas" בהגדרות ה-API. גם אם חושפים אותן, לתפקיד `anon` אין אליהן גישה.

## 1. פתיחת משתמשים (Provisioning)

כשמוסיפים גננת, איש קשר או איש צוות, או אחרי ייבוא מהאקסל, השרת עובר על הרשימה ופותח משתמשים:

```ts
const { data: pending } = await admin.schema('access').from('vw_pending_provisioning').select('*');
for (const p of pending) {
  if (p.phone) await admin.auth.admin.createUser({ phone: p.phone, phone_confirm: true });
  else         await admin.auth.admin.createUser({ email: p.email, email_confirm: true });
}
```

טריגר במסד (`trg_link_app_user`) מקשר אוטומטית את המשתמש החדש לגננת, לאיש הקשר או לאיש הצוות לפי הטלפון או המייל.
**שינוי טלפון של גננת:** צריך לעדכן גם את המשתמש ב-Supabase (`admin.auth.admin.updateUserById`).

## 2. כניסת ספק או גננת

| שלב | מה הדפדפן שולח | מה השרת עושה |
|---|---|---|
| א | סוג משתמש + מספר ספק / סמל גן | `access.login_options(user_type, login_key)` ומחזיר רק `option_id` וטלפון מוסתר |
| ב | `option_id` שנבחר | `access.resolve_login_phone(...)` ← טלפון מלא (נשאר בשרת). `access.can_send_otp(phone)` ← אם מותר: `signInWithOtp({ phone, options: { shouldCreateUser: false } })` ← `access.register_otp_sent(phone, user_type, option_id)` (רושם ביומן ההודעות ומאפס את מונה הטעויות של הקוד) |
| ג | הקוד שהוקלד | `access.verify_status(phone)`: ממשיכים רק אם `'OK'`. `'CODE_EXHAUSTED'` = הקוד נפסל אחרי 3 טעויות, מציעים לבקש קוד חדש. `'LOCKED'` = הנייד נעול. אחר כך `verifyOtp({ phone, token, type: 'sms' })`. שגוי: `access.register_failed_attempt(phone)` (מחזיר `code_exhausted` ו-`locked_until`). נכון: `access.reset_failed_attempts(phone)` |
| ד | | `access.app_user(user.id)` ← סוג המשתמש, הגן / הספק שלו ותפקיד. שומרים בסשן |

`user_type` הוא `'SUPPLIER_CONTACT'` או `'TEACHER'`.

**מדיניות נעילה (מיגרציה 10):** 3 טעויות פוסלות את הקוד הנוכחי. הנייד ננעל רק אחרי 10 כישלונות בתוך שעה, ל-15 דקות. במסך הרפרנטית: `access.vw_phone_lockouts` (נעולים עכשיו או שננעלו יותר מפעם אחת), ושחרור עם `access.unlock_phone(phone, staff_user_id)`, שנרשם ביומן הפעולות.

הודעות שגיאה כלליות בלבד ("פרטים שגויים"), כדי לא לחשוף אם מספר ספק או סמל גן קיימים.

## 3. כניסת צוות אריאל

כניסה עם חשבון העבודה של אריאל (Microsoft Entra ID, הספק `azure` של Supabase). אין קוד במייל ואין שרת מייל.

1. הכפתור "כניסה עם חשבון אריאל" הוא קישור ל-`/auth/microsoft`. השרת קורא ל-`signInWithOAuth({ provider: 'azure', options: { redirectTo: '<אתר>/auth/callback', scopes: 'email' } })` ומפנה ל-Microsoft. מפתח ה-PKCE נשמר בעוגייה.
2. Microsoft מזהה את העובדת ומחזיר אותה דרך Supabase ל-`/auth/callback` עם קוד חד-פעמי.
3. `/auth/callback` מריץ `exchangeCodeForSession(code)`, ואחר כך `access.app_user(user.id)`. רק `user_type = 'STAFF'` מקבל סשן ועובר ל-`/staff`. כל השאר מנותקים וחוזרים ל-`/login?staff=denied` עם הודעה כללית.

**פתיחת משתמש לרפרנטית:** כמו בסעיף 1, `auth.admin.createUser({ email, email_confirm: true })` עם המייל הארגוני שלה, אחרי שהיא נוספה ל-`core.staff_users`. הכתובת חייבת להיות זהה לכתובת של חשבון ה-Microsoft שלה. בכניסה הראשונה Supabase מקשר את חשבון ה-Microsoft למשתמש הקיים לפי המייל המאומת. ההרשמה העצמית כבויה, ולכן חשבון Microsoft שלא נפתח במערכת נדחה.

**הגדרות ב-Supabase:**
* Authentication, Sign In / Providers, Azure: מופעל. Client ID של האפליקציה ב-Entra ID, ו-Azure Tenant URL בצורה `https://login.microsoftonline.com/<tenant-id>` (הארגון של אריאל בלבד). את ה-Client Secret מזין אילן ישירות, והוא לא נשמר בריפו.
* Authentication, URL Configuration: Site URL הוא כתובת האתר, וב-Redirect URLs צריך להופיע `<אתר>/auth/callback` (וגם `http://localhost:3000/auth/callback` לפיתוח).

**ב-Entra ID (אצל אילן):** אפליקציה ל-"My organization only", Redirect URI מסוג Web אל `https://<project-ref>.supabase.co/auth/v1/callback`, וה-optional claim בשם `xms_edov` (ב-idToken וב-accessToken). לכל פרויקט Supabase נוסף צריך להוסיף Redirect URI משלו.

## 4. אישור גננת על דיווח

בטבלה `ops.teacher_approvals` נשמרים `auth_user_id` ו-`auth_session_id` (ה-claim `session_id` מתוך ה-JWT), `phone_used`, כתובת IP, User-Agent ו-`content_hash` (SHA-256 של תוכן הדיווח).

## 5. היסטוריית שינויים

בתחילת כל טרנזקציה שמשנה נתונים:

```sql
SELECT set_config('app.actor', 'STAFF:12', true);
```

כך נשמר בטבלאות ההיסטוריה מי ביצע את השינוי.

## 6. סביבת בדיקות

הטלפונים הפיקטיביים 050-0000xxx מוגדרים ב-Supabase כ-Test Phone Numbers עם קוד קבוע, ולכן לא אמור להישלח SMS (לאמת בבדיקה הראשונה). ההגדרה בתוקף עד 28.2.2027.
את הקוד הקבוע מקבלים מהצוות. הוא לא נשמר בריפו.

## 7. עד שה-API של 019 יגיע

ה-Send SMS Hook מפנה לפונקציה זמנית שמחזירה שגיאה. כניסה עם טלפון אמיתי תיכשל עם הודעה ברורה, ורק הטלפונים של סביבת הבדיקות יעבדו.
